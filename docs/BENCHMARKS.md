### 抽帧：单次解码 vs 逐槽解码（同素材同参数，A/B 实测）

| 实现 | 耗时 | 备注 |
|---|---|---|
| 逐槽 3 次完整解码（旧 `demo.ps1`） | **35.77s** | 每槽各解码一遍整片 |
| 单次解码 + `split=3`（现默认） | **12.09s** | **2.96×** |

两者产出的 720 张 PNG **逐帧 SHA256 完全一致**，属纯提速、无行为变化。
`-LegacyExtract` 可切回旧实现复测。

滤镜图（中间产物里的 `fg.txt`，由脚本按槽位数与 ROI 自动生成；下面是 2560×1440 基准下的取值）：

```
fps=2,split=3[b0][b1][b2];[b0]crop=760:50:1800:125[s0];[b1]crop=760:50:1800:178[s1];[b2]crop=760:50:1800:230[s2]
```

其它分辨率按 `scale = 高度 / 1440` 等比换算并贴右边缘（1080p 为 `570:38:1350:…`）。

ffmpeg 9.0 已移除 `-filter_complex_script`，须用 `-/filter_complex <file>`。

### 全流程分阶段耗时（同素材，120s）

| 阶段 | debug | release | release + 批处理 |
|---|---|---|---|
| 抽帧（单次解码 + split=3） | 12.1s | 12.1s | 12.2s |
| OCR（720 次） | 116.6s | 53.0s | **36.8s** |
| 切片 4 段 + concat 拼接 | 8.9s | 8.5s | 8.4s |
| **合计** | **138.0s** | **74.0s** | **57.8s** |

单帧 OCR 从 162ms（debug）→ 73ms（release）→ 51ms（release + 批处理）。

### 批处理：省 1.45×，但批长有拐点

`kfocr --list <文件>` 一次进程内处理多张图，模型只加载一次。批长对速度影响极大：

| 批长 | OCR 总耗时 | 单帧 |
|---|---|---|
| 逐帧一个进程（`-SingleOcr`） | 52.2s | 72ms |
| 30 帧/批 | 35.9s | 50ms |
| **60 帧/批（默认）** | **37.0s** | 51ms |
| 120 帧/批 | 64.8s | 90ms |
| 一次 720 帧 | 68–90s | 95–133ms |

同一台机、同一批帧，只改批长，单帧耗时相差 2.5×。批长超过约 60 后进程内会明显劣化，
脚本因此按 `-ChunkSize`（默认 60）分段调用。

与 CPU 亲和性、每帧 stderr 日志量都无关：做过 P 核 / E 核绑定对照（90–101ms 无差异）
和 `--quiet` 对照（60.2 / 65.3s，与不静音无差别），均不改变结论。原因未完全定位。

### 测量过程的坑（备查）

这台机在持续跑分下会明显降频：同一条命令在不同时间点能差 2×（40 帧批早期 47.5ms/帧、
后期 90ms/帧）。因此本目录所有性能结论都取自成对/交替测量（同一时刻的 A、B 对比），
绝对秒数只用于量级参考。中途曾因这一点得出「批处理更慢」的错误结论，靠 6 轮交替配对才纠正。

## §OCR 前置过滤与帧间去重（2026-11-24 复测）

环境：RTX 4070 / 16 线程 / ffmpeg 9.0 / kfocr release（opt3 + lto）。
两台素材都是 120s / 2560×1440 / 60fps 的 ShadowPlay 录像，参数默认（scan-fps 2、pre 3.5 / post 1.5）。

### 端到端

| 阶段 | 素材 A（`2026.11.21 - 23.24.02.04`） | 素材 B（`2026.11.11 - 23.21.53.04`） |
|---|---|---|
| 抽帧 | 9.35s → 7.5–9.4s（实现未变，波动来自机器降频） | 7.34s |
| OCR | **32.3s → 3.0s** | **32.3s → 2.7s** |
| 切片 + 拼接（4 段） | 9.3s → 8.9s（实现未变） | 8.4s |
| **合计** | **51.2s → 19.7s（2.6×）** | **41.0s → 18.6s（2.2×）** |

两条素材在优化前后的**成片 SHA256 完全一致**（25.52s / 52.4MB 与 21.02s / 54.2MB），
所以这是纯提速、零行为变化：`--no-prefilter --no-dedup --ocr-jobs 1` 可以回到旧行为做 A/B。
过滤与去重做在 `kfocr` 里、默认开启，所以 PowerShell 引擎（`highlight.ps1`）走同一份二进制，
同样直接受益（`test-parity.mjs` 里 PS 侧一条素材 50s+ → 28s，两侧成片仍逐字节一致）。

### OCR 为什么能砍掉 78%

`kfocr` 现在在 `engine.recognize_bgra` 之前做两件微秒级的事（两者都不加载模型）：

1. **前置空槽过滤**：扫描裁剪图的像素，算「击杀条底色（青绿 + 红）」占比；低于 6%、
   且行首金框也低于 1% 就判为空槽，直接跳过推理。
2. **帧间去重**：把图像降采样成 32×8 灰度块，和同槽位上一帧算平均绝对差（MAD），
   低于 0.012 就复用上一帧的识别结果（同一行停留 4–5s，2fps 下连续 6–10 帧几乎不变）。
   槽位切换（父目录变化）时缓存自动失效。

| | 素材 A（720 帧） | 素材 B（723 帧） |
|---|---|---|
| 推理帧数 | 720 → **159** | 723 → **139** |
| 跳过：空槽 / 帧间重复 | 428 / 133 | 451 / 133 |
| 得到文本行 | 232 → 160 | 205 → 133 |
| 与基线的事件判定 | 完全一致 | 完全一致 |

阈值是拿 `rows.json` 当标注标定出来的（素材 A）：真击杀行的底色占比最低 **0.1191**、
空槽帧 p95 只有 **0.0511**，阈值 0.06 两边都有 2× 余量；行首金框做兜底
（真击杀帧 0.024–0.042，噪声帧 0–0.020），所以「换配色/换滤镜导致底色判据失灵」也不会丢击杀。
误判成「有内容」只是多跑一次推理，代价可接受；反过来会丢击杀，因此判据刻意宁松勿紧。

换地图 / 改 HUD 缩放 / 游戏大版本更新后想复核这套阈值，用 `scripts/bench-kfocr-filter.mjs`：
先用 `--keep-work --no-prefilter --no-dedup` 留一份现场，再跑它就能看到三分位分布与阈值扫描，
「丢真击杀帧 0」才算安全（脚本会以退出码 1 提醒）。素材 B 复核结果同样是 0 丢帧，余量 2.36×。

### 分块并发（`--ocr-jobs`）

单个 `kfocr` 进程只吃 60 张（批长拐点，见上一节），进程内并行度用不满，多进程才吃得下 CPU：

| `--ocr-jobs` | 1 | 2 | 3 | 4（默认 auto） |
|---|---|---|---|---|
| OCR 720 帧（过滤后 159 张推理） | 13.2s | 6.6s | 4.6s | **3.8s** |

四种并发的成片逐字节一致。并发行序不确定会影响「自动推断本机 ID」的平票结果，
所以收完 `rows` 会按 `(slot, t)` 重排，回到 PS 引擎的遍历顺序 —— 两个引擎仍给出同一个 ID
（`scripts/test-parity.mjs` 两条素材均 PASS）。

### 负结果：整片硬件解码比软解更慢

| 配置（120s / 7200 帧） | 解码到 null | 抽帧到 720 张 PNG |
|---|---|---|
| 软解（现默认） | 9.90s | 9.45s |
| `-hwaccel cuda` | 12.45s | 12.38s |
| `-hwaccel d3d11va` | 15.48s | — |
| 软解 + `-skip_frame nokey`（GOP 0.5s） | — | 5.37s |
| **`-hwaccel cuda` + `-skip_frame nokey`** | — | **1.29s** |

原因：整片硬解要把每一帧 1440p 从显存拷回内存（滤镜链在 CPU 侧），7200 帧的拷贝开销
超过软解本身；只有「每 0.5s 才要一帧」时硬解才有优势。所以 `--hwaccel` 默认 **off**，
只在 `--extract keyframe` 里自动生效。

### 关键帧抽帧（`--extract keyframe`）：快 7×，但会改结果

ShadowPlay 的 GOP 实测 **0.5s**（120s 里 241 个关键帧），刚好等于 2fps 的取样间隔，
所以「只解关键帧」在时间上够密。但它是 **opt-in**，原因有三：

1. 取样帧与 `fps` 滤镜选中的帧可能差 ±1 帧（源是 VFR，2fps 网格与关键帧 PTS 有 ±0.5ms 抖动）；
2. 硬件解码的像素与软解不完全一致（PSNR 41–45dB，肉眼与 OCR 都无感）；
3. 结论会变：素材 A 上 6 杀变 5 杀 —— 少的那条是 OCR 噪声变体（`乐邦詹士HC小奶萝` 与
   `乐邦詹士小奶萝` 被旧路径当成两次击杀），属于「换了取样帧，噪声不再复现」；
   时间戳整体有 ±0.5s 偏移。

两者叠加时：抽帧 9.45s → **1.21s**，全流程 12.6s（含切片 7.6s）。

### 编码侧：`--encoder nvenc` 与 `--fast-copy`

25s / 1440p 成片的实测（同一素材、同一段区间）：

| 配置 | 耗时 | 体积 |
|---|---|---|
| `libx264 -preset veryfast -crf 20`（默认，4 段合计 9.0s） | 9.0s | 52.4MB |
| `h264_nvenc -preset p4 -cq 24` | 8.0s | 86.4MB |
| `-c copy` 无损直剪（`--fast-copy`） | **0.6s** | 100.1MB |
| `--cut-jobs 4`（x264） | 8.8s | 52.4MB |

- **nvenc 只快 ~10%**：1440p/60fps 下 NVENC 本身~2.4ms/帧，而 x264 veryfast 已经很快；
  同画质体积约 1.7×（`-cq` 与 `-crf` 不是同一把尺，要对齐体积得往上加 cq）。
  `-hwaccel cuda` 配 nvenc 也没有收益（软解已经喂得饱），所以切片阶段不加硬解。
- **`--fast-copy` 才是这一阶段的真赢家**：9.0s → 0.6s、零画质损失。
  代价是每段首尾对齐到关键帧（GOP 0.5s → 成片 26.04s vs 25.52s、体积 100.1 vs 52.4MB，
  因为直剪保留源码率而不是重新压到 crf 20）。`--cut-jobs` 没意义（x264 已吃满核心）。

### 结论

| 用法 | 端到端 | 代价 |
|---|---|---|
| 默认（什么都不配） | **19.7s** | 成片与旧版逐字节一致 |
| `--fast-copy` | ~11s | 体积 ≈2×；每段时间 +≤1 GOP（0.5s） |
| `--extract keyframe`（GOP≤0.5s） | ~13s | 取样帧差 ±1 帧，个别 OCR 噪声判定会变 |
| 两者同开 | **~5.9s** | 上述两项代价叠加 |
